# GTM Bridge: состояние и безопасное обновление

Дата: 2026-08-20.

## Результат

Текущий `gtm-mcp` на сервере работает как отдельный MCP-сервис, но его сборка
устарела примерно на пять месяцев и не даёт Jungle подключаться к инструментам.
Причина не в доступе к Google Ads или Google Analytics. Это несовместимость
авторизации между Jungle и старой HTTP-версией GTM MCP, а также хранение
Google OAuth-сессии только в памяти процесса.

У upstream есть актуальная версия `v1.8.2` с двумя подходящими возможностями:

- удалённый MCP по OAuth 2.1 + PKCE для веб-клиентов;
- service-account режим для постоянного служебного доступа к Google Tag Manager.

## Что установлено сейчас

- Сервис: `gtm-mcp` на `https://gtm-mcp.kazanflowerschool.com`.
- Проверка здоровья проходит после пересоздания контейнера 2026-08-20.
- Образ не содержит source URL, номера версии или commit SHA; поэтому его
  точный исходный commit доказать нельзя.
- По строкам бинарника модуль называется `gtm-mcp-server`, а OAuth-хранилище
  использует `MemoryTokenStore`. После перезапуска такая сессия не является
  постоянной.
- Jungle видит удалённый сервер, но не завершает OAuth 2.1 + PKCE к upstream,
  поэтому список инструментов пуст.

## Источник и актуальность

Публичный проект, соответствующий модулю и набору функций: 
<https://github.com/sprawz/gtm-mcp-server>.

На 2026-08-20 upstream имеет 171 commit, последняя помеченная версия `v1.8.2`
(2026-08-06), а ветка `main` обновлялась 2026-08-18. В ней есть управление
web и server-side контейнерами, версиями, публикацией и безопасными
подтверждениями для рискованных операций.

## Целевая схема

1. Отдельный Google service account получает доступ только к нужным GTM
   контейнерам Margariteros.
2. Новый `gtm-mcp` использует этот service account для вызовов GTM API.
3. Jungle подключается к `gtm-mcp` по внутренней сети с отдельным служебным
   ключом. Личный Google OAuth для этого не используется.
4. Внешние веб-клиенты используют OAuth самого MCP-сервера, если они нужны.
   Доступ к Google остаётся внутри Bridge и не передаётся клиентам.
5. Изменения создаются в рабочем пространстве GTM. Публикация версии остаётся
   действием человека до отдельного решения владельца.

## Минимальные права

- Для Bridge: `Edit` только на нужных контейнерах.
- `Approve` нужен, только если Bridge должен создавать версии.
- `Publish` не выдавать, пока автоматическая публикация отдельно не одобрена.
- Не выдавать Bridge права администратора аккаунта, управления пользователями
  или удаления, если эти действия не требуются.
- У GTM должны остаться минимум два живых человеческих администратора.

## Порядок миграции

1. Собрать новый образ из закреплённого commit upstream, а не из плавающего
   `main`.
2. Создать service account и дать ему ограниченный доступ в GTM.
3. Хранить JSON-ключ service account и ключ доступа Jungle только в OpenBao.
4. Поднять второй контейнер рядом со старым и проверить только чтение:
   аккаунты, контейнеры, рабочие пространства, теги и триггеры.
5. Переключить Jungle на новый Bridge после успешного чтения.
6. Оставить прежний контейнер как rollback до отдельного подтверждения
   удаления.

## Ограничения

- Это не меняет существующие теги, события, GTM-контейнеры, сайты или рекламу.
- GTM API имеет известное ограничение: условия `autoEventFilter` у некоторых
  click/form triggers могут не сохраниться через API. Такие условия нужно
  делать вручную в интерфейсе GTM.
- Если service account нельзя добавить в GTM, резервный вариант -- OAuth
  отдельного технического пользователя с offline refresh token в OpenBao и
  consent screen в Production. Это менее надёжно, чем service account.
